## Q1 — คีย์จับคู่รายการข้ามปี (item matching key)

**(ก) เหตุใดต้องตัดสินใจ:** การจับคู่รายการคือรากของ MODE 1 ทั้งหมด (กฎ Y01–Y13)
ถ้าจับคู่ผิด รายการเดิมจะถูกรายงานเป็น "รายการใหม่ + รายการหาย" พร้อมกัน
และผลต่างจำนวนเงินทุกจุดจะผิดความหมายทั้งชุด

**(ข) ทางเลือก (บันไดตามกรอบที่กิ๊ฟให้):**
1. รหัสทางการที่ปรากฏเหมือนกันทั้งสองปี (`official_code`)
2. รหัสร่วมกับระดับลำดับชั้นหรือรหัสรายการแม่ (`code_plus_hierarchy`)
3. รหัสร่วมกับชื่อและบริบทของหมวด (`code_plus_name_context`)
4. ชื่อหลัง normalize — เป็น candidate เท่านั้น (`normalized_name`, suggest-only)
5. fuzzy matching — เสนอให้มนุษย์ตรวจเท่านั้น ห้ามยืนยันอัตโนมัติ (`fuzzy_name`)

**(ค) ผลกระทบ:** เปิดเฉพาะขั้น 1–2 → จับคู่แม่นแต่ unmatched เยอะ งาน review เพิ่ม ·
เปิดถึงขั้น 4–5 → ครอบคลุมขึ้นแต่ทุกคู่จากขั้นเหล่านี้ต้องผ่านมนุษย์ก่อนเสมอ
(ระบบบังคับ suggest-only ไว้แล้ว) · การเลือก "ฟิลด์บริบท" ของขั้น 2–3 ผิด
จะทำให้รายการที่ย้ายโครงสร้าง (Q7) จับคู่ไม่ได้

**(ง) หาจากไฟล์อัตโนมัติได้ไหม:** ได้บางส่วน — inventory รายงานแล้วว่า
คอลัมน์ใดมีลักษณะรหัส (pattern + จำนวนค่าไม่ซ้ำ) และค่ารหัสของสองไฟล์
คาบเกี่ยวกันกี่เปอร์เซ็นต์ (`code_column_overlap`) ซึ่งบอกได้เชิงประจักษ์ว่า
รหัสน่าจะคงที่ข้ามปีหรือไม่ · แต่**เลือกบันไดและฟิลด์ไม่ได้เอง**

**(จ) ต้องยืนยัน:** ① คอลัมน์ใดคือรหัสทางการ ② ลำดับขั้นของบันไดและฟิลด์บริบทแต่ละขั้น
③ นิยาม normalize ชื่อ (ตัดช่องว่าง/วงเล็บ/แปลงเลขไทย-อารบิกหรือไม่)
④ เกณฑ์ขั้นต่ำของ suggested match ที่จะแสดงให้ review

ข้อบังคับที่ล็อกไว้ในโค้ดแล้ว: ห้ามใช้เลขแถว/ลำดับเป็นตัวระบุข้ามปี
(`mapping_model` ปฏิเสธ `row_order`) · ทุก match เก็บ วิธี / คีย์ / confidence /
หลักฐานฝั่ง A และ B / สถานะ exact–rule_based–suggested / เหตุผลที่มนุษย์ยืนยันหรือปฏิเสธ
(ตาราง `item_matches`)

## Q2 — ชีตที่ต้องตรวจ และช่วงแถวข้อมูล

**(ก) เหตุใด:** ฟอร์มราชการมี header หลายชั้น + merged cells + ชีตหลายบทบาท
ตรวจผิดชีตหรือเริ่มผิดแถว = ตรวจผิดเอกสารทั้งฉบับ · ห้ามถือว่าชีตชื่อเดียวกัน
มีบทบาทเดียวกันทุกไฟล์/ทุกปี

**(ข) ทางเลือก:** ① ตรวจเฉพาะชีตรายละเอียด (source/detail) ② ตรวจ detail + summary
พร้อมกฎกระทบยอด (Y11/R06) ③ ตรวจทุกชีตที่มีตาราง · และต่อชีต: เลือกบทบาทจากชุด
source_detail / summary / investment / allocation / supporting_reference /
non_data_presentation

**(ค) ผลกระทบ:** เฉพาะ detail → เร็ว แต่มองไม่เห็นความไม่สอดคล้องระหว่าง detail
กับ summary · รวม summary → ได้กฎกระทบยอดแต่ต้องยืนยันทิศทางการอ้างสูตรก่อน ·
ทุกชีต → ครอบคลุมสุดแต่ noise สูงและช้า

**(ง) อัตโนมัติได้ไหม:** ได้ระดับ "ข้อเสนอ" — inventory สร้าง sheet-role proposal
จากหลักฐานจริง: ชีตที่มีสูตรอ้างชีตอื่น (ลักษณะสรุป) กับชีตที่ถูกอ้าง (ลักษณะต้นทาง)
พร้อมจำนวนสูตรและตัวอย่าง cell reference · แถบหัวตารางและช่วงข้อมูลเสนอเป็น candidate
พร้อมเกณฑ์ที่ใช้ตรวจ

**(จ) ต้องยืนยัน:** ① บทบาทของทุกชีตในทุกไฟล์ ② แถบหัวตาราง ③ แถวเริ่ม–สิ้นสุดข้อมูล
④ แถวผลรวมที่ไม่ใช่รายการ (กันบวกซ้ำ) — ทั้งหมดจะอยู่ใน MAPPING_DECISION_FORM
พร้อมหลักฐานสูตร/ตำแหน่งตามที่กิ๊ฟสั่ง

## Q3 — คอลัมน์จำนวนเงิน หน่วย และสเกลจัดเก็บ

**(ก) เหตุใด:** ถ้าเข้าใจหน่วยผิด (บาท ↔ ล้านบาท) ผลต่างผิดเป็นล้านเท่าทั้งรายงาน
และเอกสารจริงมักประกาศหน่วยหนึ่งแต่จัดเก็บอีกสเกลหนึ่ง

**(ข) ทางเลือก:** ① normalize ทุกค่าเป็นบาทก่อนเทียบ ② เก็บตามหน่วยเอกสารและเทียบ
เฉพาะคู่ที่หน่วยเดียวกัน (ถ้าหน่วยต่างให้หยุดและรายงาน) ③ เทียบ stored value ดิบ
โดยไม่แปลง

**(ค) ผลกระทบ:** ① สะดวกที่สุดแต่พังทั้งระบบถ้า scale ผิด — จึงต้องมีหลักฐานยืนยันก่อน
(ระบบบังคับ: `scale_to_baht` ที่ไม่มี evidence จะไม่ผ่าน validate) ·
② ปลอดภัยสุดแต่จะเทียบเอกสารต่างหน่วยไม่ได้ · ③ เสี่ยงเทียบผิดความหมายเมื่อสองไฟล์
เก็บต่างสเกล

**(ง) อัตโนมัติได้ไหม:** หา "หลักฐาน" ได้ครบ — inventory รายงาน declared unit
พร้อมตำแหน่ง (เช่น เซลล์ "หน่วย : ล้านบาท"), number format ต่อคอลัมน์
(เช่น `#,##0.0000` ที่มักคู่กับล้านบาท), ค่า stored กับ displayed แยกกัน ·
แต่**ตัดสิน scale ไม่ได้เอง**

**(จ) ต้องยืนยัน:** ต่อคอลัมน์เงินทุกคอลัมน์: declared unit · scale factor ·
จำนวนทศนิยมที่มีนัย · และเลือกทางเลือก ①/②/③ — จนกว่าจะยืนยัน
**ระบบจะไม่ normalize** และจะรายงานแยก stored / displayed / number format /
declared unit / normalized (ช่องหลังว่างไว้) ตามที่กิ๊ฟกำหนด

## Q4 — กติกาลำดับชั้นโครงสร้าง (แผนงาน → ผลผลิต/โครงการ → กิจกรรม → รายการ)

**(ก) เหตุใด:** ใช้กับกฎ Y10 (ย้ายโครงสร้าง), Y11/R06 (ยอดรวมสัมพันธ์รายการย่อย),
R10 (ผลกระทบรายระดับ) — ถ้าอ่านชั้นผิด การ roll-up ยอดผิดทั้งต้นไม้
และจะกล่าวหาว่า "ยอดไม่สัมพันธ์" ทั้งที่สัมพันธ์ดี

**(ข) ทางเลือก:** ① คอลัมน์ระดับชั้นเฉพาะ (เช่น ค่าตัวเลขระดับ) ② โครงรหัส
(รหัสยาวขึ้น/จุดคั่นตามความลึก) ③ รูปแบบการเยื้อง (indent) หรือตัวหนาของชื่อรายการ
④ แถวหัวข้อคั่นกลุ่ม — เอกสารจริงอาจใช้ผสมกัน

**(ค) ผลกระทบ:** แต่ละแบบต้องเขียน parser ต่างกัน · เดาผิดหนึ่งชั้น
พ่อลูกสลับ → กฎผลรวมรายงานเท็จเป็นระบบ

**(ง) อัตโนมัติได้ไหม:** หา "ร่องรอย" ได้ — inventory รายงานคอลัมน์ที่มี indent
หลายระดับ (พร้อมจำนวน), รหัสแบบจุดคั่น, แถวตัวหนาที่ไม่มีตัวเลข ·
เลือกกติกาไม่ได้เอง

**(จ) ต้องยืนยัน:** กติกาลำดับชั้นต่อชีต (เลือกแบบ ①–④ หรือผสม พร้อมพารามิเตอร์)
และตัวอย่างสายลำดับชั้น 2–3 สายที่กิ๊ฟยืนยันว่าอ่านถูก ก่อนระบบใช้ roll-up จริง

## Q5 — บทบาทของเกณฑ์ร้อยละ (±10%)

**(ก) เหตุใด:** ต้องกำหนดชัดว่าร้อยละมีบทบาทอะไร เพื่อไม่ให้กลายเป็นเกณฑ์ตัดสินถูกผิดโดยพลัด

**(ข)–(ค) กิ๊ฟตอบแล้ว (26 ส.ค.):** ±10% **ไม่ใช่เกณฑ์ตัดสินถูกผิด** —
ใช้ได้เพียง ① ตัวกรองช่วยจัดลำดับการตรวจ ② threshold ของระดับความสำคัญ
③ ค่าที่ผู้ใช้ตั้งได้ต่องาน · ระบบต้องแสดงผลต่างจริง**ทุกจุด**ในขอบเขตกฎ:
amount A · amount B · ผลต่างสัมบูรณ์ · ร้อยละ (เมื่อมีฐานคำนวณที่เหมาะสม) ·
ตำแหน่งหลักฐานทั้งสองฝั่ง · **ห้าม**ทำให้ผลต่าง <10% หายไป และ**ห้าม**เรียก >10%
ว่า error อัตโนมัติ — ล็อกในโค้ดแล้ว: `thresholds.role = "highlight_only"` เท่านั้นที่ผ่าน validate

**(ง) อัตโนมัติได้ไหม:** ไม่ต้องหา — เป็นนโยบาย ไม่ใช่ข้อเท็จจริงในไฟล์

**(จ) เหลือยืนยัน (เล็กน้อย):** ① ค่า default ต่อโหมด (เสนอ 10% ปรับได้ต่องาน)
② วิธีรายงานร้อยละเมื่อฐานเป็นศูนย์หรือว่าง — **ข้อเสนอ:** แสดง "คำนวณร้อยละไม่ได้
(ฐาน = 0/ว่าง)" แทนการใส่ตัวเลขใด และไม่นับเข้า filter ร้อยละ

## Q6 — ค่าคลาดเคลื่อนที่ยอมรับได้ในการเทียบยอด (tolerance)

**(ก) เหตุใด:** ทศนิยมและการปัดของ Excel ทำให้ค่าที่เท่ากันเชิงบัญชี
ต่างกันเชิง floating point · แต่ tolerance ที่กว้างเกินจะกลบผลต่างจริง —
อันตรายเป็นพิเศษเมื่อหน่วยเป็นล้านบาท: ค่า 0.5 ที่เคยใช้ใน validator เดิม
ถ้าไฟล์เก็บเป็นล้านบาท เท่ากับยอมให้คลาด **500,000 บาท** ซึ่งยอมรับไม่ได้

**(ข) ทางเลือก:** ① tolerance สัมบูรณ์ผูกกับหน่วยของคอลัมน์ (เช่น 0.00005 ลบ. = 50 บาท)
② เทียบหลังปัดตามจำนวนทศนิยมที่เอกสารแสดง ③ เทียบค่า stored แบบ exact
(tolerance = 0)

**(ค) ผลกระทบ:** ①/② ตัด noise จากการปัดได้ · ③ เข้มสุดแต่จะรายงานความต่างระดับ
เศษทศนิยมที่ไม่มีนัยจำนวนมาก → ผู้ตรวจล้า · ทุกแบบ**ไม่ซ่อนค่า**: ระบบแสดงผลต่างจริงเสมอ
tolerance ใช้เพียงแยกป้าย "ตรงกัน" กับ "พบความแตกต่าง"

**(ง) อัตโนมัติได้ไหม:** เสนอได้จาก number format จริง (เช่น ทศนิยม 4 ตำแหน่ง
ในหน่วยล้านบาท → เสนอ tolerance ครึ่งหนึ่งของหลักสุดท้าย = 0.00005 ลบ.) —
เป็น candidate ต้องยืนยัน

**(จ) ต้องยืนยัน:** ค่า tolerance ต่อคอลัมน์/หน่วย (หลังยืนยัน Q3)
และยืนยันว่าให้ตั้งค่าต่องานได้แบบเดียวกับ threshold

## Q7 — นิยาม "รายการที่ย้ายแผนงาน/ผลผลิต/โครงการ/หมวด/หน่วยงาน" (กฎ Y10)

**(ก) เหตุใด:** รายการที่คีย์จับคู่ได้แต่ไปอยู่ใต้โครงสร้างอื่น จะนับเป็น
"ย้าย" (Y10 หนึ่งรายการ) หรือ "หายจากที่เดิม + ใหม่ในที่ใหม่" (Y05+Y04 สองรายการ)
— กระทบทั้งยอดสรุปจำนวนข้อแตกต่างและปริมาณงาน review

**(ข) ทางเลือก:** ① ถ้าคีย์จับคู่ได้แต่ parent ต่าง → รายงานเป็น Y10 หนึ่งรายการ
(สถานะ ต้องให้มนุษย์ตรวจสอบ) ② นับเป็น Y05+Y04 สองรายการเสมอ
③ เสนอเป็น suggested match ให้มนุษย์ยืนยันว่า "ย้าย" เป็นรายกรณี

**(ค) ผลกระทบ:** ① กระชับและตรงความหมายเมื่อคีย์เชื่อถือได้ ·
② ปลอดภัยเมื่อคีย์ไม่แน่น แต่ยอดข้อแตกต่างจะบวม ·
③ แม่นสุดแต่งาน review มากสุด

**(ง) อัตโนมัติได้ไหม:** ตรวจ "parent ต่างกัน" ได้อัตโนมัติเมื่อ Q1 (คีย์) และ Q4
(ลำดับชั้น) ยืนยันแล้ว · ตัดสิน "เป็นการย้ายจริง" ไม่ได้เอง

**(จ) ต้องยืนยัน:** ① เลือกวิธีนับ ①/②/③ ② นิยาม parent ที่ใช้เทียบ
(เทียบเฉพาะแผนงาน หรือทั้งสาย แผนงาน→ผลผลิต→กิจกรรม)
**ข้อเสนอของระบบ:** ใช้ ① โดย Y10 มี machine status = ต้องให้มนุษย์ตรวจสอบ เสมอ
และแสดงสาย parent เดิม–ใหม่คู่กันเป็นหลักฐาน

- CLI ปฏิเสธการเขียนรายงานลงโฟลเดอร์ที่มี "OneDrive" ในเส้นทาง
  (ข้ามได้เฉพาะสั่ง `--allow-onedrive` อย่างชัดแจ้ง)
- ไฟล์จริงที่กิ๊ฟจะจัดให้: ระบบ**อ่านตรงจากโฟลเดอร์ที่กิ๊ฟแจ้ง** ไม่คัดลอกไปที่อื่น
  และพิสูจน์ทุกครั้งว่าไม่แก้ไฟล์ด้วย SHA-256 ก่อน/หลัง
- ไม่มีสิ่งใดต้องยืนยันเพิ่ม เว้นแต่กิ๊ฟต้องการเปลี่ยนตำแหน่ง `.data\`
  (เปลี่ยนได้ด้วย `REDBOOK_DATA_DIR`)
