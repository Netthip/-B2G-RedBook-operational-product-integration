## A. ข้อจำกัดสี่เรื่องที่ Gift สั่งให้รายงานเป็นการเฉพาะ

### A1. roll-up / การกระทบยอด — **ยังไม่มีในระบบเลย**

commit ที่ตรึงไว้ **ไม่มีโมดูล roll-up** (`redbook/t1b/rollup.py` เพิ่งเข้าที่ commit `3d9d5ad`
ซึ่งอยู่**เหนือ** commit ที่ตรึง จึงไม่ถูกใช้ในรอบนี้ — เป็นการตรึงโดยตั้งใจ)

สิ่งที่ระบบ **ไม่ได้** ตรวจ:

* ผลรวมของแถวลูก เท่ากับยอดของแถวแม่ในตารางเดียวกันหรือไม่
* ผลรวมของหมวดงบรายจ่ายรายคอลัมน์ เท่ากับคอลัมน์ `รวม` หรือไม่
* ผลรวมของแผนงานทุกแผน เท่ากับยอด `รวมทั้งสิ้น` ของหน่วยงานหรือไม่
* ยอดของปีหนึ่งที่ยกไปเป็นยอดตั้งต้นของปีถัดไป สอดคล้องกันหรือไม่

**นัยต่อการใช้ผล** finding ที่ระบบออกให้เป็น **การเทียบทีละเซลล์ล้วน ๆ**
ถ้าแถวแม่กับแถวลูกไม่สอดคล้องกันภายในแฟ้มเดียวกัน ระบบจะไม่รู้ และจะไม่มี finding ใดชี้ให้
ในรอบนี้พบตัวอย่างที่ยืนยันได้ว่า *ถ้ามี roll-up จะช่วยได้* คือกลุ่ม finding ที่มี
`difference` เท่ากันเป๊ะข้ามหลายแถวในชีตเดียวกัน (แถวแม่และแถวลูกขยับพร้อมกัน) —
รอบนี้ต้องอาศัยคนสังเกตเอาเอง

### A2. cross-sheet — **ยังไม่มีในระบบเลย**

ระบบเทียบ **แฟ้มต่อแฟ้ม ชีตต่อชีต** โดยผูก identity ด้วย `sheet_role` ที่ได้จากเลขข้อในหัวเรื่อง
**ไม่มีการยันข้ามชีตแม้แต่คู่เดียว**

สิ่งที่ระบบ **ไม่ได้** ตรวจ:

* ยอดรวมของหน่วยงานในชีตปก ตรงกับยอดในชีตบทบาท `SECTION_04` / `SECTION_05` / `SECTION_06` หรือไม่
* ยอดรายแผนงานในชีตบทบาท `SECTION_06` ตรงกับยอดในชีตแผนงาน (`SECTION_07_PLAN`) หรือไม่
* ยอดหน่วย **บาท** ในชีตปกและข้อ 6.1 ตรงกับยอดหน่วย **ล้านบาท** ที่อื่นหรือไม่
  (นี่คือจุดที่ควรจับ error หน่วยได้ดีที่สุด และเป็นจุดที่ยังว่างอยู่)

**นัยต่อการใช้ผล** ยอดเดียวกันที่ปรากฏในหลายชีต ถูกตรวจแยกกันหมด
ถ้าแก้ที่ชีตหนึ่งแต่ลืมแก้อีกชีตหนึ่ง ระบบจะออก finding ที่ชีตที่แก้เท่านั้น
และผู้อ่านจะไม่มีทางรู้จากรายงานว่ามันควรจะเท่ากัน

### A3. formula residue — **มองไม่เห็นสูตร เห็นแต่ค่าที่ถูก cache ไว้**

ระบบเปิดแฟ้มด้วย `openpyxl` โหมด `data_only=True` แปลว่า:

* อ่านได้เฉพาะ **ค่าที่ Excel คำนวณไว้ล่าสุดแล้วบันทึกติดแฟ้มมา**
* **ไม่เห็นตัวสูตร** จึงไม่รู้ว่าเซลล์นั้นเป็นค่าที่พิมพ์มือหรือมาจากสูตร
* ถ้าแฟ้มถูกบันทึกโดยเครื่องมือที่ไม่คำนวณสูตร ค่าที่อ่านได้จะเป็น `None` และกลายเป็น
  `UNRESOLVED` / `UNMAPPED` โดยระบบ **ไม่สามารถแยกได้** ว่า "ไม่มีค่า" กับ "สูตรยังไม่ถูกคำนวณ" ต่างกัน
* **ไม่ตรวจ** สูตรที่ชี้ไปช่วงที่ผิด สูตรที่ถูก hard-code ทับ หรือค่า error (`#REF!` `#VALUE!` ฯลฯ)
  ที่ตกค้างในแฟ้ม

**หลักฐานจากรอบนี้** รายงาน inventory ของแฟ้ม baseline บันทึกไว้ตั้งแต่ 27 ส.ค. 2569 ว่ามีชีตประกอบหนึ่งชีต
ที่ *"สูตรไม่มีค่า cache 0 · ค่า error 36"* — ในรอบนี้ชีตนั้นตกเป็น `UNMAPPED` 32 record
**โดยไม่มี finding ใดบอกว่าเป็นเพราะค่า error** ผู้อ่านรายงานจะเห็นแค่ "ยังไม่ map"

### A4. approved-adjustment classification — **ยังไม่มีในระบบเลย**

ระบบออกได้แค่ *อะไรเปลี่ยน* และ *ต้องดูตรงไหน* ตามหลัก **"ระบบเสนอ · มนุษย์ตัดสิน"**
**ไม่มีชั้นใด** ที่แยก:

* การปรับตามมติ/หนังสือที่อนุมัติแล้ว ออกจาก การเปลี่ยนที่ยังไม่ทราบเหตุ
* การปรับที่เกิดจากการแถลงตัวเลขปีที่ปิดแล้วใหม่ ออกจาก การปรับกรอบงบปีอนาคต
* การเปลี่ยนที่เป็นผลสืบเนื่องจากอีกการเปลี่ยนหนึ่ง ออกจาก การเปลี่ยนที่เป็นอิสระ

**นัยต่อการใช้ผล** ในรอบนี้มี finding ที่ยอดเปลี่ยน **77 ใบ** — ทั้ง 77 ใบมีสถานะเท่ากันหมดในสายตาระบบ
ต้องให้คนอ่านทีละใบและตัดสินเอง ระบบไม่ได้ช่วยลดจำนวนใบที่ต้องอ่าน
และไม่มีที่เก็บคำตัดสินของคนเพื่อให้รอบถัดไปไม่ต้องถามซ้ำ

## B. ข้อจำกัดเพิ่มเติมที่พบจากการรันจริงรอบนี้

### B1. หัวเรื่องชีตถูกแย่งโดยเซลล์ข้อความตัวแรกที่เจอ — **ทำให้ชีตหลักทั้งชีตหลุดจากการตรวจได้**

การหาหัวเรื่องชีตไล่จากแถว 1 ถึงแถว 4 **ทีละแถว จากซ้ายไปขวาทุกคอลัมน์** แล้วหยิบข้อความแรกที่ไม่ว่าง
ถ้ามีเซลล์ข้อความสั้น ๆ ที่เป็น flag ของเครื่องมือสร้างแฟ้มวางอยู่ในคอลัมน์ขวาสุดของแถวก่อนหัวเรื่องจริง
ระบบจะได้ flag นั้นเป็นหัวเรื่อง ⇒ ไม่มีเลขข้อ ⇒ ชีตถูกจัดเป็น `SUPPORTING` ⇒ **ทั้งชีตกลายเป็น `UNMAPPED`**

รอบนี้เกิดขึ้นจริง **1 ชีต** ในแฟ้ม current (ชีตแผนงานบทบาท `SECTION_07_PLAN`)
ผลคือ 72 record ของแฟ้ม baseline ออกมาเป็น `ROW_REMOVED` **ทั้งที่แผนงานนั้นยังอยู่ในแฟ้ม current**
⇒ **false positive 72 ใบจากสาเหตุเดียว** และแผนงานที่มีสัดส่วนงบมากที่สุดของหน่วยงานไม่เคยถูกเทียบ

`accounted()` ยังครบ (record ไม่หาย) แต่ **ความครบของ accounting ไม่ได้แปลว่าความครบของการตรวจ**
ข้อนี้เป็นตัวอย่างที่ชัดที่สุดว่า invariant ที่ระบบมีอยู่ยังไม่พอสำหรับการรับประกันความครอบคลุม

### B2. ตารางแกน `BUDGET_CATEGORY` ไม่บันทึกปี ⇒ finding เทียบข้ามปีโดยไม่ติดป้าย

record ที่มี `comparison_axis = BUDGET_CATEGORY` ถูกบังคับให้ `fiscal_year = None`
ตาม truth table ของ `axis_valid` (แกนปีกับแกนหมวดต้องเป็น **XOR** กัน)

แต่ตารางจำแนกหมวดงบรายจ่ายในแฟ้มจริง **ผูกกับปีของแฟ้ม** — หัวเรื่องชีตบทบาท `SECTION_06`
ระบุปีงบประมาณไว้ชัดเจน และเป็นคนละปีในสองแฟ้ม
เมื่อจับคู่ด้วยลายเซ็นที่มี `fiscal_year = None` เท่ากันทั้งสองฝั่ง จึงได้ finding ที่
**เทียบยอดปีหนึ่งกับยอดอีกปีหนึ่ง โดยช่อง `fiscal_year` ว่าง** ปนอยู่ในไฟล์เดียวกับ finding ที่เทียบปีเดียวกัน

**ขนาดในรอบนี้** 34 คู่จาก 236 คู่ที่จับคู่ได้ (14.4%) เป็นแกนหมวดที่ `fiscal_year` ว่าง
ในนั้น **12 คู่ออกเป็น `AMOUNT_INCREASED` / `AMOUNT_DECREASED`**

**นี่คือเกณฑ์หยุดทันทีข้อ 6** ("ผลดูสมเหตุสมผลแต่เทียบคนละปี") — บันทึกเป็น observation ไม่แก้ในรอบนี้

### B3. รหัสหน่วยงานอ่านจากชื่อไฟล์เท่านั้น — ด่านกันการเทียบข้ามหน่วยงานไม่ทำงานกับชื่อไฟล์จริง

`agency_code` เป็นฟิลด์ **identity** ใน `t1b-key-0.1.0` แต่ระบบอ่านค่ามาจาก
รูปแบบชื่อไฟล์ `XL_FY####_<status>_#####_` เท่านั้น
ชื่อแฟ้มจริงของหน่วยงานไม่ตรงรูปแบบนี้ ⇒ `agency_code` เป็น **ค่าว่างทั้งสองฝั่ง**
⇒ คีย์ยังเท่ากัน ⇒ จับคู่ได้ตามปกติ **แต่ไม่มีการยืนยันว่าเป็นหน่วยงานเดียวกัน**

รอบนี้ไม่เกิดความเสียหาย (ทั้งสองแฟ้มเป็นหน่วยงานเดียวกันจริง) แต่ถ้าป้อนแฟ้มคนละหน่วยงาน
**ระบบจะไม่ทักท้วง** ทั้งที่ชื่อหน่วยงานอ่านได้ถูกต้องจากชีตปก (แต่ไม่ถูกใช้เป็นด่าน)
`document_status` (draft-bill / revised-per-act) ก็หายไปด้วยเหตุเดียวกัน

### B4. ชีตปกยังไม่ map ⇒ ยอดรวมของเอกสารไม่เคยถูกเทียบ

ชีตปกถูกจัดเป็น `COVER` และ layout ยังไม่ map (`cover_sheet_layout_not_mapped`)
⇒ 17 record ต่อแฟ้ม (34 record รวม) กลายเป็น `UNMAPPED`
**ยอดงบประมาณรายจ่ายรวมของหน่วยงานอยู่ในชีตนี้** และเป็นยอดหน่วย **บาท**
ซึ่งเป็นยอดเดียวที่ทานกับเอกสารอื่นได้ตรงที่สุด — จึงเป็นช่องว่างที่ควรปิดก่อนใช้งานจริง

เช่นเดียวกับข้อ 6.1 ของชีตบทบาท `SECTION_06` (ตารางจำแนกตามลักษณะรายจ่าย หน่วย **บาท**)
ที่อยู่นอกตารางรายปีและตารางหมวด ⇒ ตกเป็น `rows_outside_year_table_not_mapped`

### B5. เกณฑ์ `COVER` ยังเป็น `DATASET-BOUNDED HEURISTIC`

การจัดชีตแรกของแฟ้มที่ไม่มีเลขข้อให้เป็น `COVER` ยืนยันแล้วกับชุดข้อมูล T1B **6 แฟ้มเท่านั้น**
แฟ้มจากหน่วยงานอื่นหรือปีอื่นอาจวางชีตปกไว้ตำแหน่งอื่น — **ต้องทบทวนก่อนขยายชุดข้อมูล**
(ข้อนี้โค้ดเตือนไว้เองใน docstring แล้ว)

### B6. บทบาทชีตรั่วเข้าชีตประกอบที่ซ่อนอยู่

ชีตประกอบ (mask) ที่ซ่อนอยู่ 2 ชีตต่อแฟ้ม ได้บทบาท `SECTION_04` และ `SECTION_02`
เพราะหัวเรื่องของมันมีเลขข้อ ทั้งที่เป็นชีตทำงานภายในของเครื่องมือสร้างแฟ้ม
รอบนี้ยังไม่ก่อความเสียหาย (ไม่มีตารางรายปี จึงตกเป็น `UNMAPPED` ทั้งชีต)
แต่ถ้าชีต mask ในแฟ้มอื่นบังเอิญมีตารางที่ตรงรูปแบบ **จะไหลเข้าผลการตรวจจริงทันที**

### B7. record `UNMAPPED` เป็นเสียงรบกวนหลักของรายงาน

`UNMAPPED` **810 record** = 46.2% ของ record ทั้งหมด และกลายเป็น finding 810 ใบ
= 52.8% ของ finding ทั้งหมด · ทุกใบติดธง "ต้องให้มนุษย์ตรวจ"

ในทางออกแบบถูกต้อง (invariant ข้อ 1–2: ห้ามทิ้งเงียบ) แต่ในทางใช้งาน
**คิวมนุษย์ 1,284 ใบ ที่ 63% เป็น `UNMAPPED` ของชีตประกอบ/mask ทำให้คิวเสียความหมาย**
ต้องมีการแยกชั้น (เช่น "ยังไม่ map เพราะเป็นชีตประกอบ" vs "ยังไม่ map ทั้งที่เป็นชีตหลัก")
ก่อนส่งให้คนใช้จริง

### B8. `PROJECT_ORDINAL_CHANGED` ยังพิสูจน์ไม่ได้ด้วยคู่แฟ้มนี้

detector ทำงานและออก **0 finding** ซึ่งถูกต้องสำหรับคู่นี้ (ไม่มีโครงการที่เลขลำดับเปลี่ยน)
แต่ **0 ที่ถูกต้อง ไม่ใช่หลักฐานว่า detector จับได้จริง** — ในคู่นี้โครงการเดียวที่มีทั้งสองฝั่ง
ไม่ถูกจับคู่ตั้งแต่ต้นเพราะแผนงานแม่เปลี่ยนชื่อ ต้องรอคู่แฟ้มที่มีการสลับลำดับจริงจึงจะยืนยันได้

### B9. ไม่มีการเทียบกับ PDF และไม่มีการตรวจซ้ำด้วยแหล่งที่สอง

รอบนี้อ่าน **เฉพาะ `.xlsx`** ทั้งที่ในคลังมี PDF ของทั้งสองแฟ้มอยู่ครบ
ไม่มีขั้นตอนใดยันว่าตัวเลขใน Excel ตรงกับเล่มที่พิมพ์จริง

### B10. ไม่มีการตรวจแถวซ่อน คอลัมน์ซ่อน และ merged cell ที่คร่อมความหมาย

ระบบบันทึกจำนวน merged cell ไว้เป็น provenance แต่ **ไม่ได้ใช้ในการตัดสินความหมาย**
และไม่มีการรายงานแถว/คอลัมน์ที่ซ่อนอยู่ในชีตหลัก (แฟ้ม baseline มีแถวซ่อนตามรายงาน inventory เดิม)
ค่าที่อยู่ในแถวซ่อนถูกอ่านเข้ามาเทียบเหมือนแถวปกติ โดยรายงานไม่บอกผู้ตรวจว่าแถวนั้นซ่อนอยู่
