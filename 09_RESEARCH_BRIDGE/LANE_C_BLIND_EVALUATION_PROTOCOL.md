ข้อบกพร่องสังเคราะห์ **โดยไม่สร้างและไม่ดู answer key**"*

**ผู้ร่าง:** Giho · **ร่างแรก** 5 กันยายน 2569 · **ป้ายกำกับ:** `PRODUCT EVIDENCE — POST-FREEZE`

**สถานะ:** 🔴 **`DRAFT — NOT YET EXECUTED`** · **ฉบับแก้ครั้งที่ 1** (6 กันยายน 2569)

> ## 🔴 การแก้ครั้งที่ 1 — ตามคำตัดสิน Bo (`BO REVIEW COMPLETE` · 6 ก.ย. 2569)
>
> *"Revise scoring into separate output layers … A referral is not an automatic TP

> **สิ่งที่เปลี่ยน** — หมวด 5 เดิมให้ Gift เลือกว่ารายการที่ส่งเข้าคิวมนุษย์นับเป็น
> `TP` / ไม่นับ / `FP` · **คำตัดสินยกเลิกทางเลือกทั้งสาม** แล้วให้แยกเป็น
> **สามชั้นการให้คะแนน** แทน ⇒ ตัดคำตัดสินข้อนั้นออกจากหมวด 9 แล้ว

> **เหตุผล** — การยุบเป็นสองค่าสร้างแรงจูงใจให้ดัน `F1` ให้สูงด้วยการโยนทุกอย่าง
> เข้าคิวมนุษย์ ซึ่งทำให้ตัวเลขดูดีขึ้นโดยที่ระบบไม่ได้ดีขึ้น

> เอกสารนี้เป็น **ข้อกำหนดล่วงหน้า** เท่านั้น · เกณฑ์ทุกข้อต้องตรึงก่อนเปิดผล

## 1. สิ่งที่โปรโตคอลนี้วัด และไม่วัด

| วัด | ไม่วัด |
|---|---|
| ความสามารถของ detector ในการ **พบ** ข้อบกพร่องที่ถูกใส่ไว้ | ความพึงพอใจของผู้ใช้ |
| ความสามารถในการ **ระบุตำแหน่งและชนิด** ให้ถูก | เวลาที่ประหยัดได้ |
| อัตราการเตือนผิดบนแฟ้มที่สะอาด | ความถูกต้องของตัวเลขในเอกสารต้นทาง |
| ความคงเส้นคงวาของผลเมื่อรันซ้ำ | ความปลอดภัยของระบบ (แยกไปหมวด security) |

### 🔴 ข้อห้ามที่หนักที่สุด — คำที่ห้ามใช้สลับกัน

**การรันซ้ำด้วย input เดิม วัด `ความคงเส้นคงวา / ทำซ้ำได้` ไม่ใช่ `ความแม่นยำ`**

⇒ ห้ามเขียนว่า *"รันซ้ำได้ผลเท่าเดิม จึงแม่นยำ"* เด็ดขาด
⇒ ตัวเลขความถูกต้องมาจาก **การเทียบกับเฉลยที่ปิดไว้เท่านั้น**

และเนื่องจากในงานตรวจสอบเอกสาร **true negative มีจำนวนมหาศาล** (เซลล์ที่ไม่มีข้อบกพร่อง)
🔴 **ห้ามรายงาน `accuracy` ดิบ** เพราะจะสูงเกือบ 100% เสมอโดยไม่มีความหมาย
เกณฑ์ `≥90%` ที่จะประกาศต้อง **ระบุว่าเป็นตัวชี้วัดใด** เสมอ

## 2. บทบาทที่ต้องแยกจากกัน — ข้อกำหนดเชิงระเบียบวิธี

| บทบาท | หน้าที่ | 🔴 ห้าม |
|---|---|---|
| **ผู้สร้างชุดทดสอบ** | สร้างแฟ้มสะอาด · ใส่ข้อบกพร่อง · เขียนเฉลย | ห้ามแตะโค้ด detector · ห้ามดูผลก่อนปิดผนึก |
| **ผู้พัฒนา detector** | พัฒนาและตรึงเวอร์ชัน | 🔴 **ห้ามเห็นเฉลย** · ห้ามเห็นรายการข้อบกพร่อง |
| **ผู้ให้คะแนน** | เทียบผลที่ปิดผนึกกับเฉลย | ห้ามแก้ผลหรือเฉลย |

🔴 **ข้อห้ามที่ Gift ระบุตรง ๆ** — ห้ามให้ตัวแทนเดียวกัน *สร้างข้อบกพร่อง* →
*ดูเฉลย* → *ปรับ detector กับเคสนั้น* แล้วเรียกผลว่า **blind**

**สถานะปัจจุบัน:** 🔴 ยังไม่มีการแยกบทบาทนี้ — **เป็นคำตัดสินที่ต้องขอจาก Gift**
ทางเลือกที่เห็น: (ก) Gift เป็นผู้สร้างชุดทดสอบเอง · (ข) ให้ agent คนละตัวที่ไม่มีสิทธิ์
อ่านโค้ด detector เป็นผู้สร้าง · (ค) สร้างล่วงหน้าแล้วปิดผนึกก่อนพัฒนา detector รอบถัดไป

## 4. บัญชีชนิดข้อบกพร่องที่เสนอ — **ยังไม่สร้างจริง**

> 🔴 ตารางนี้เป็น **บัญชีชนิด** ไม่ใช่เฉลย · ไม่มีที่ใดในเอกสารนี้ระบุว่า
> ข้อบกพร่องตัวใดจะถูกใส่ที่ตำแหน่งใดหรือกี่ตัว

| `V-02` | ยอดแม่เปลี่ยน แต่ลูกไม่เปลี่ยน | ทิศตรงข้ามของ `V-01` |
| `V-03` | ผลรวมรายหมวดไม่เท่าคอลัมน์ `รวม` | ตรงกับกฎ `CATEGORY_SUBTOTALS_TO_TOTAL` |

## 5. การให้คะแนน **สามชั้น** — ห้ามยุบเป็น TP/FP คู่เดียว

> 🔴 **คำตัดสิน Bo · 6 กันยายน 2569** — *"Do not force human-review referrals into a
> binary TP/FP choice. That would conflate automatic correctness with useful
> escalation. … A referral is not an automatic TP and is not automatically an FP.
> It must be scored in its own stratum."*
>
> คำตัดสินนี้ **แทนที่** ข้อเสนอเดิมของเอกสารฉบับนี้ที่ให้ Gift เลือกทาง
> (ก) `TP` · (ข) ไม่นับ · (ค) `FP` — **ไม่ต้องเลือกอีกแล้ว** เพราะทั้งสามทางล้วนผิด
> ในทางระเบียบวิธี · เหตุผลที่ Bo ให้ไว้: การยุบเป็นสองค่าสร้าง **แรงจูงใจให้ดัน F1
> ให้สูงด้วยการโยนทุกอย่างเข้าคิวมนุษย์**

### 5.1 ชั้น ① — การตัดสินอัตโนมัติ (automatic determination)

นับเฉพาะรายการที่ระบบ **ฟันธงเอง** เท่านั้น · รายการที่ส่งเข้าคิวมนุษย์ **ไม่เข้าชั้นนี้**

| ตัวชี้วัด | นิยาม |
|---|---|
| `TP` | ข้อบกพร่องที่ใส่ไว้ และระบบฟันธงถูก **ทั้งตำแหน่งและชนิด** |
| `TP-loc` | ตำแหน่งถูก ชนิดผิด — 🔴 **นับแยก ห้ามรวมกับ `TP`** |
| `FP` | ระบบฟันธงว่าเป็นปัญหา แต่ไม่ตรงกับข้อบกพร่องใดในเฉลย |
| `FN` | ข้อบกพร่องในเฉลยที่ระบบ **ไม่ฟันธงและไม่ส่งต่อ** |
| `precision` ① | `TP / (TP + FP)` |
| `recall` ① | `TP / (TP + FN + ข้อบกพร่องที่ถูกส่งต่อแทนการฟันธง)` |
| `F1` ① | ค่าเฉลี่ยฮาร์มอนิกของสองตัวข้างบน |

🔴 **ตัวหารของ `recall` ① ต้องรวมรายการที่ถูกส่งต่อด้วย** มิฉะนั้นการโยนของยาก
เข้าคิวมนุษย์จะทำให้ `recall` ① สูงขึ้นเองโดยที่ระบบไม่ได้เก่งขึ้นเลย

### 5.2 ชั้น ② — การส่งต่อให้มนุษย์ (human-review referral)

| ตัวชี้วัด | นิยาม |
|---|---|
| `referral-correct` | ส่งต่อ **และชี้ตำแหน่งถูก** — ข้อบกพร่องจริงอยู่ตรงที่ชี้ |
| `referral-wrong` | ส่งต่อโดยที่ไม่มีข้อบกพร่องตรงนั้น (รบกวนคนโดยไม่จำเป็น) |
| `referral-missed` | ข้อบกพร่องที่ **ควรถูกส่งต่อแต่ไม่ถูกส่ง** และระบบก็ไม่ฟันธง |
| `referral recall` | `referral-correct / (referral-correct + referral-missed)` |
| **ภาระการตรวจ** | จำนวนรายการที่ส่งเข้าคิว **ต่อ 1,000 record** |

🔑 ชั้นนี้ตอบคำถามคนละข้อกับชั้น ① — *"ระบบพาคนไปดูถูกที่หรือเปล่า"*
ไม่ใช่ *"ระบบตัดสินถูกหรือเปล่า"*

🔴 **ภาระการตรวจต้องรายงานคู่เสมอ** — `referral recall` ที่สูงเพราะส่งทุกอย่างเข้าคิว
ไม่มีค่าในทางปฏิบัติ · ตัวเลขคู่นี้ต้องอ่านด้วยกัน

### 5.3 ชั้น ③ — ความครอบคลุมรวม (overall detection coverage)

| ตัวชี้วัด | นิยาม |
|---|---|
| `coverage` | ข้อบกพร่องที่ **ระบบฟันธงถูก หรือ ส่งต่อถูกจุด** ÷ ข้อบกพร่องทั้งหมด |
| `uncovered` | ข้อบกพร่องที่ทั้งไม่ถูกฟันธงและไม่ถูกส่งต่อ — **หลุดทั้งระบบ** |

🔴 **ต้องรายงานแยกจาก `F1` ① เสมอ ห้ามนำมาแทนกัน** — `coverage` วัดว่า
*"กระบวนการทั้งกระบวนการ (ระบบ + คน) มีโอกาสเจอไหม"*
ส่วน `F1` ① วัดว่า *"ระบบตัดสินเองได้ดีแค่ไหน"*

### 5.4 ตัวหารที่ต้องประกาศทุกครั้ง — ทั้งสามชั้น

* จำนวนข้อบกพร่องที่ใส่ทั้งหมด **แยกรายชนิด**
* จำนวนรายการที่ **อยู่นอกความสามารถที่ประกาศไว้** (หมวด 4) —
  🔴 รายงานแยก **ห้ามนับเป็น `FN` เงียบ ๆ**
* จำนวน record ทั้งหมด (ตัวหารของภาระการตรวจ)
* จำนวนรายการในชุด negative control

### 5.5 กติกาการรายงานที่ผูกกับสามชั้นนี้

1. 🔴 **ห้ามรายงานตัวเลขเดียวเป็น "ความแม่นยำของระบบ"** — ต้องมีครบสามชั้น
2. 🔴 **ห้ามรายงาน `accuracy` ดิบ** — true negative ท่วม จะสูงเกือบ 100% เสมอ
3. เกณฑ์เป้าหมายต้อง **ระบุชั้นและตัวชี้วัด** เช่น *"`recall` ① ≥ …"*
   ไม่ใช่ *"ความแม่นยำ ≥ 90%"*
4. การรันซ้ำ input เดิม วัด **ความคงเส้นคงวา** ไม่ใช่ค่าใดในสามชั้นนี้

## 6. Clean negative control

รันชุดแฟ้ม **ที่ไม่มีข้อบกพร่องเลย** แล้ววัดว่าระบบแจ้งกี่ใบ

| ตัวชี้วัด | ความหมาย |
|---|---|
| จำนวน finding ที่ระบบฟันธงว่าเป็นปัญหา | ควรเป็น **0** |
| จำนวนที่ส่งเข้าคิวมนุษย์ | ยิ่งน้อยยิ่งดี แต่ **ไม่ใช่ข้อผิดพลาด** |
| อัตราต่อ 1,000 record | ทำให้เทียบข้ามชุดข้อมูลได้ |

🔴 ตัวเลขนี้สำคัญเป็นพิเศษกับระบบนี้ เพราะ `UNMAPPED` คิดเป็น **46%** ของ record
ในการรันจริง — ถ้าไม่วัด negative control เลข recall จะดูดีโดยไม่มีความหมาย

## 7. หลักฐานที่ต้องเก็บทุกครั้ง — หกชั้น

3. เวอร์ชันส่วนประกอบทุกตัว
4. seed ของ generator
5. คำสั่งที่รันจริง + เวลา + timezone
6. สภาพแวดล้อม (ภาษา · ไลบรารี · ระบบปฏิบัติการ)
