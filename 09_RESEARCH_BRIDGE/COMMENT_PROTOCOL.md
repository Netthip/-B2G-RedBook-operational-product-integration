## 1. โครงคอมเมนต์ (ใช้ทุกครั้ง)

```markdown
**[ชนิด]** ผู้ส่ง → ผู้รับ · ตอบ <id คอมเมนต์ หรือ "เปิดเรื่อง">

**สรุป:** (1–3 บรรทัด — อ่านบรรทัดนี้บรรทัดเดียวต้องรู้เรื่อง)

**ขอจาก <ผู้รับ>:** (สิ่งที่ต้องทำ/ตัดสิน เป็นข้อ ๆ — หรือเขียน "ไม่มี — แจ้งเพื่อทราบ")

**หลักฐาน:** `<commit>` · [ไฟล์รายงาน](ลิงก์) · tests N passed

<details><summary>รายละเอียด (ไม่ต้องอ่านถ้าไม่ตรวจลึก)</summary>

...ไม่เกินครึ่งหน้า ถ้ายาวกว่านี้ให้ย้ายไปไฟล์...

</details>
```

**ขนาด:** ส่วนที่มองเห็น (นอก `<details>`) **ไม่เกิน 1,200 ตัวอักษร** · ทั้งคอมเมนต์ **ไม่เกิน 3,000**
เกินกว่านั้น = ต้องเป็นไฟล์

### ชนิด (เหลือ 6 ชนิด)

| ชนิด | ใช้เมื่อ | แทนป้ายเดิม |
|---|---|---|
| `HANDOFF` | ส่งงานให้อีกฝ่ายตรวจ | HANDOFF READY FOR BO |
| `REVIEW` | ผลตรวจ — ต้องมีคำตัดสิน `ACCEPT` / `REVISE` / `REJECT` บรรทัดแรกของสรุป | BO REVIEW COMPLETE · RESEARCH REVIEW |
| `ASK-GIFT` | ต้องให้กิ๊ฟตัดสิน — เขียนเป็นตัวเลือก ก/ข/ค | DECISION REQUIRED FROM GIFT |
| `CLAIM` | ประกาศว่ากำลังจะทำเลน/ไฟล์ใด | LANE CLAIM |
| `FINDING` | เจอปัญหา/ความเสี่ยง/ข้อสังเกต | ENGINEERING OBSERVATION · RISK · EVIDENCE |
| `ACK` | รับทราบ ไม่มีเนื้อหาใหม่ — **หนึ่งบรรทัดพอ** | — |

ป้ายเสริมเดิม (`SYNTHETIC ONLY` · `NOT AN AUTHORITY` ฯลฯ) ใส่ต่อท้ายบรรทัดแรกได้ ไม่ต้องขึ้นบรรทัดใหม่

## 2. รายงานยาวไปไว้ที่ไหน

```
09_RESEARCH_BRIDGE/threads/<เลขใบ>/<YYYY-MM-DD>_<ชนิด>_<หัวข้อสั้น>.md
```

ตัวอย่าง `threads/08/2026-09-27_HANDOFF_personnel-quarterly.md`

แก้ไฟล์ภายหลังได้ แต่คำตัดสินที่อ้างถึงยังผูกกับ commit เดิม

**ฝ่ายที่แนบไฟล์ใน repo ไม่ได้ (Bo):** ใส่เนื้อหายาวไว้ใน `<details>` ได้ แต่คงโครงสรุป/ขอจาก ไว้ด้านบน
แล้ว Giho จะย้ายลงไฟล์ให้เมื่อเกิน 3,000 ตัวอักษร (ข้อความเดิมคงไว้ ไม่แก้คอมเมนต์ของ Bo)

## 3. "ใครต้องทำต่อ" ดูจากป้าย ไม่ต้องอ่านทั้งกระทู้

ทุกใบที่เปิดอยู่มีป้าย `รอ:` **ได้ทีละหนึ่งอัน**

| ป้าย | ความหมาย |
|---|---|
| `รอ:โบ` | ลูกอยู่ที่ Bo |
| `รอ:จีโฮ` | ลูกอยู่ที่ Giho |
| `รอ:กิ๊ฟ` | รอคนตัดสิน — ถ้าติดนาน ให้ทำใบอื่นต่อ (กติกาสี่เลน) |

ผู้โพสต์เป็นคนย้ายป้ายไปหาผู้รับทุกครั้ง · หน้า Issues กรองด้วย `label:รอ:โบ` ได้ทันที

---

## 4. ตัวใบเก็บ "สถานะปัจจุบัน" — คอมเมนต์ไม่ต้องเล่าซ้ำ

ส่วนบนของเนื้อหาใบ (issue body) มีกล่อง

```markdown
## สถานะปัจจุบัน (แก้ล่าสุด YYYY-MM-DD)
- ทำแล้ว: ...
- ค้าง: ...
- คำตัดสินที่ผูกพัน: ... (ลิงก์คอมเมนต์)
```

**แก้ในที่เดิม** ทุกครั้งที่มีคำตัดสินหรือส่งงาน (Giho เป็นคนแก้ · Bo ขอให้แก้ได้ผ่าน `ขอจาก`)
คอมเมนต์ใหม่จึงไม่ต้องเริ่มด้วยการสรุปสถานะทั้งหมดซ้ำ

## 5. หนึ่งใบหนึ่งเรื่อง · ใบยาวแล้วตัดรอบ

- เรื่องใหม่ที่โผล่กลางใบ → เปิดใบใหม่ แล้วคอมเมนต์ในใบเดิมหนึ่งบรรทัด `แยกไป #N`
- ใบใดเกิน **25 คอมเมนต์** หรือได้คำตัดสินหลักแล้ว → Giho โพสต์คอมเมนต์ปิดรอบ
  (สรุป ≤ 10 บรรทัด + ลิงก์คำตัดสินทั้งหมด) แล้วปิดใบ เปิดใบต่อถ้ายังมีงาน
- ห้ามแก้หรือลบคอมเมนต์เก่าที่มีคำตัดสินอ้างถึง (append-only เหมือนเดิม)

## 8. Bo ตอบอัตโนมัติ

คอมเมนต์ที่เจ้าของรีโพโพสต์ และบรรทัดแรกมี **`→ Bo`** จะปลุก GitHub Actions ให้ Bo
(OpenAI API · system prompt = [`BO_AGENT_BRIEF.md`](BO_AGENT_BRIEF.md) + ไฟล์นี้) อ่านใบนั้นแล้วตอบในใบเดียวกัน
จากนั้นย้ายป้ายไป `รอ:จีโฮ` หรือ `รอ:กิ๊ฟ` เอง

- Bo อ่าน: ตัวใบ · คอมเมนต์ล่าสุด 12 อัน · ไฟล์ในรีโพนี้ที่คอมเมนต์ปลุกลิงก์ถึง — **มองไม่เห็นรีโพ private**
- คำตอบโพสต์ในชื่อ `github-actions[bot]` ท้ายคอมเมนต์มีป้าย 🤖 · **ไม่ใช่คำตัดสินของกิ๊ฟ**
- เบรก: ตอบอัตโนมัติได้ไม่เกิน 6 ครั้งต่อใบต่อ 24 ชม. เกินแล้วหยุดและส่งลูกให้กิ๊ฟ
- ปลุกด้วยมือ: แท็บ Actions → *Bo reply* → Run workflow → ใส่เลขใบ
- ปิดชั่วคราว: Actions → *Bo reply* → Disable workflow

`thread_digest.py` คัดเฉพาะบรรทัด `[ชนิด]` และ `สรุป:` ของแต่ละคอมเมนต์ —
ถ้าทุกคนเขียนตามโครง ข้อ 1 การอ่านย้อนทั้งใบจะเหลือไม่กี่บรรทัด
