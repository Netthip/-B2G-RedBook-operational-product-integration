## 1. ขอบที่ไม่ปลอดภัยก่อนแก้ (`bb399a0`)

`check_identity()` ออกผลสี่สถานะอยู่แล้ว แต่ `match_records()` หยุดเฉพาะ
`IDENTITY_CONFLICT` เท่านั้น อีกสามสถานะไหลผ่านไปจับคู่ตามปกติ

| สถานะ | ความหมาย | พฤติกรรมที่ `bb399a0` |
|---|---|---|
| `IDENTITY_OK` | ยืนยันได้ว่าหน่วยงานเดียวกัน | จับคู่ ✅ ถูกต้อง |
| `IDENTITY_CONFLICT` | คนละหน่วยงานแน่ชัด | ปฏิเสธ ✅ ถูกต้อง |
| `IDENTITY_UNVERIFIED` | อ่านตัวตนจากเนื้อในไม่ได้ | 🔴 **จับคู่ต่อ** |
| `IDENTITY_AMBIGUOUS` | ฝั่งหนึ่งมีตัวตนมากกว่าหนึ่งค่า | 🔴 **จับคู่ต่อ** |

### ผลที่วัดได้จริงก่อนแก้

วัดด้วย `scripts/t1b_identity_gate_probe.py` บน worktree ของ `bb399a0`
(สมุดงาน **สังเคราะห์** · แฟ้มละ 5 record)

```
FAIL  S1 ตัวตนว่างทั้งสองฝั่ง — จับคู่อัตโนมัติ 3 คู่; AMOUNT_* 3 ใบ;
                                provenance สองฝั่งไม่ครบในคิวมนุษย์
FAIL  S2 ตัวตนว่างฝั่งเดียว    — ROW_ADDED 3 ใบ; ROW_REMOVED 3 ใบ;
                                provenance สองฝั่งไม่ครบในคิวมนุษย์
FAIL  S2b ตัวตนว่างอีกฝั่ง     — ROW_ADDED 3 ใบ; ROW_REMOVED 3 ใบ; …
ok    S3 ชื่อหน่วยงานขัดแย้งกัน
ok    S4 หน่วยงานเดียวกัน — ยังจับคู่ได้ 3 คู่
สรุป: ละเมิดสัญญา 3 ฉาก   (exit 1)
```

🔴 **ประเด็นที่ต้องอ่านให้ตรง** — อันตรายไม่ได้อยู่ที่ "จับคู่ผิด" อย่างเดียว
เมื่อตัวตนว่าง **ฝั่งเดียว** คีย์สองฝั่งต่างกันจึงไม่มีคู่เกิดขึ้น แต่ระบบกลับ
**สรุปเอง**ว่าทุกแถว *ถูกลบ* และ *ถูกเพิ่ม* — ซึ่งก็เป็นการตัดสินอัตโนมัติ
ที่ตั้งอยู่บนสมมติฐานว่าสองแฟ้มเทียบกันได้ ทั้งที่ยังไม่มีหลักฐานรองรับ

## 2. กติกาหลังแก้

**ทางผ่านมีทางเดียว** — ประกาศเป็นชุด *ที่อนุญาต* ไม่ใช่ชุด *ที่ห้าม*

```python
IDENTITY_MAY_MATCH = frozenset({IDENTITY_OK})
```

⇒ เหตุผลใหม่ที่ยังไม่มีในวันนี้จะตกไปทาง **ปฏิเสธ** โดยอัตโนมัติ
(ทดสอบไว้ที่ `test_g6_gate_is_closed_by_default_for_unknown_reasons`)

### ผลระดับการเปรียบเทียบ

Bo สั่งให้กรณีที่ถูกกันต้องคืน *comparison-level result* ไม่ใช่แค่ไม่มีคู่

| เหตุผลของด่าน | ผลระดับการเปรียบเทียบ | เหตุผลของการแบ่ง |
|---|---|---|
| `IDENTITY_OK` | `COMPARED` | เทียบจริง |
| `IDENTITY_CONFLICT` | `REVIEW_REQUIRED` | มีหลักฐาน**ชี้ชัด**ว่าผิดฝาผิดตัว — คนตัดสินได้ทันที |
| `IDENTITY_UNVERIFIED` | `CANNOT_DETERMINE` | หลักฐาน**ไม่พอ**จะตัดสิน — ต้องหาหลักฐานเพิ่มก่อน |
| `IDENTITY_AMBIGUOUS` | `CANNOT_DETERMINE` | เช่นเดียวกัน |
| *(เหตุผลที่ไม่รู้จัก)* | `CANNOT_DETERMINE` | ค่าเริ่มต้นอยู่ข้างปฏิเสธเสมอ |

### สิ่งที่ยัง **ต้องไม่**หายเมื่อถูกกัน

1. `accounted()` = จำนวน record ขาเข้ารวมสองฝั่ง — ห้าม silent drop
2. ทุก record อยู่ในคิวมนุษย์พร้อมป้ายฝั่ง (`baseline` / `current`)
3. `Finding.detail` มีเหตุผลของ **ด่าน** *ต่อกับ* เหตุผลของ **รายการนั้นเอง**
   — ต่อกัน **ไม่ใช่แทนที่** มิฉะนั้น provenance รายรายการจะหาย

## 5. ข้อจำกัดที่ยังเปิดอยู่

1. ตัวตนหน่วยงานอ่านจาก **ชีตปก** ของแฟ้มชุดนี้ — ยังเป็น dataset-bounded
   แฟ้มที่วางชื่อหน่วยงานไว้ที่อื่นจะได้ `CANNOT_DETERMINE` (ซึ่งตอนนี้ **ปลอดภัย**
   เพราะไม่เทียบ แต่แปลว่ายังใช้กับแฟ้มนอกชุดนี้ไม่ได้)
2. เมื่อด่านปฏิเสธ ระบบยังไม่มี **ทางให้มนุษย์ยืนยันตัวตนด้วยมือ** แล้วเดินต่อ —
   เป็นงานของ Lane B (คิวและหน้าจอ) และต้องเป็นการกระทำที่บันทึก audit trail
3. `IDENTITY_AMBIGUOUS` ยังพิสูจน์ได้เฉพาะที่ระดับ `check_identity()`
   เพราะ adapter ของชุดข้อมูลนี้อ่านชีตปกแรกเพียงชีตเดียว
